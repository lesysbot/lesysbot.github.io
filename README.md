# lesysbot-docs

The documentation site for [LeSysBot](https://github.com/lesysbot/lesysbot) and its
official Linux, macOS, and Windows tool collections.

**Live at <https://lesysbot.github.io/>**

Static HTML and Tailwind CSS, generated by a small Node script. No framework,
no client-side router, no runtime dependencies — the published site is plain
files plus one stylesheet and one 8 KB script for search and the version
switcher.

## Quick start

```bash
npm install
npm run build      # → dist/
npm run serve      # → http://localhost:4173/
```

`npm run dev` rebuilds HTML and CSS on change while serving.

## How it is put together

```
content/
  site.json              site name, base path, repo URLs
  versions.json          every published version; which one is "latest"
  v0.1/
    nav.json             sidebar order
    tools.json           the tool catalog — every package and tool
    guides/*.md          guide pages, frontmatter + markdown
src/
  build.js               the generator
  lib/                   markdown, layout, tool pages, highlighting
  styles/main.css        the Tailwind theme and every component class
  assets/                site.js and the favicon, copied verbatim
scripts/
  import-docs.js         pull guide markdown from a local core-repo checkout
  release.js             cut a new documentation version
  check-links.js         fail the build on a broken internal link
  serve.js               local preview under the real base path
```

Everything the build reads lives in `content/`. The core repo is not needed to
build the site — `import-docs.js` is a convenience for refreshing guide text,
not a build step.

## Versioning

Each version is built into its own directory and stays there permanently:

```
/                        → redirects to /latest/
/latest/                 → the newest version
/v0.1/                   → frozen at the 0.1.0 release
/v0.1/guides/usage/      → permanent URL, never moves
/versions/               → the version index
/versions.json           → machine-readable manifest
```

The version dropdown in the header switches between them. It keeps you on the
same page where that page exists in the target version, and falls back to that
version's home page where it does not — so switching never lands on a 404.

### Cutting a new version

When LeSysBot tags a release:

```bash
node scripts/release.js v0.2 --label 0.2.0 --ref v0.2.0 --notes "Windows service support."
```

That snapshots `content/v0.1/` into `content/v0.2/`, marks 0.1 archived, and
points `latest` at 0.2. From then on you edit `content/v0.2/`; everything under
`/v0.1/` is frozen exactly as it was published.

To pull in upstream guide changes afterwards:

```bash
node scripts/import-docs.js ../lesysbot v0.2
```

`overview.md` and `security.md` are authored in this repo and are never
overwritten by an import.

## Documenting a tool

Tool pages are generated from `content/<version>/tools.json` — there is no page
to hand-write. Add an entry to `packages` and the catalog, the package page,
the sidebar counts, and the search index all update together:

```jsonc
{
  "slug": "battery",
  "name": "battery",
  "collection": "macos",          // core | linux | macos | windows
  "version": "1.0.0",             // from the package's README frontmatter
  "summary": "Battery charge, power source, and time remaining.",
  "platforms": ["macos"],
  "requires": ["pmset"],          // binaries that must be on PATH
  "deps": [],                     // pip packages
  "tools": [
    {
      "name": "battery",
      "kind": "cli",              // cli | python
      "command": "pmset -g batt", // shown when kind is cli
      "summary": "Report charge percentage and time remaining.",
      "params": [],
      "confirm": false,
      "privileged": false
    }
  ],
  "notes": ["Free-form paragraphs rendered as a bulleted list."],
  "troubleshooting": [
    { "symptom": "…", "cause": "…", "fix": "…", "verify": "some command" }
  ]
}
```

Set `"danger": true` on a package that can power the machine off — it gets a
warning banner.

## Deployment

`.github/workflows/deploy.yml` builds on every push to `main` and publishes to
GitHub Pages. The build fails if any internal link breaks.

One-time setup: **Settings → Pages → Source → GitHub Actions**.

### Using a custom domain

Set `SITE_BASE` to an empty string and `SITE_URL` to the domain in the workflow
env, add a `CNAME` file to `src/assets/`, and point the DNS at GitHub Pages. The
generator reads both variables and rewrites every absolute URL accordingly.
